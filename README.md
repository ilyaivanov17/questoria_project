# Questoria

Questoria — образовательная игровая платформа с сюжетными миссиями, головоломками и системой прогресса.

Этот репозиторий является **единым monorepo проекта**: здесь хранятся продуктовая документация, исходный код приложения и автономный UI-прототип.

## Состав репозитория

- `quest_platform_prd.md` — основной PRD и технический blueprint.
- `questoria_mvp_execution_spec.md` — конкретная спецификация реализации MVP, API, данных, CMS и backlog.
- `questoria_master_blueprint.md` — собранный master-документ.
- `prototype/` — автономный интерактивный HTML-прототип; он не является production-приложением.
- `apps/web/` — Next.js frontend.
- `apps/api/` — NestJS backend.
- `packages/contracts/` — общие TypeScript-контракты.
- `prisma/` — схема PostgreSQL и миграции.
- `docs/ADR/` — принятые архитектурные решения (ADR-009–012).
- `infra/` — локальная инфраструктура.

## Технологическая база

- Node.js 22 LTS и pnpm 12.
- Next.js 16.4 + React + TypeScript.
- NestJS 12, REST API.
- PostgreSQL 17 + Prisma ORM 7.
- Docker Compose для локальной базы данных.

Архитектура MVP — модульный монолит. Redis, микросервисы, платежи и социальные функции на старте не добавляем.

## Локальный запуск

Требуются Node.js `22.23.5`, pnpm `12.17.0` и Docker с Compose.

```bash
nvm install
nvm use
corepack enable
pnpm install
cp .env.example .env
docker compose -f infra/docker/docker-compose.yml up -d postgres
pnpm db:generate
pnpm db:deploy
pnpm db:seed
pnpm dev
```

После запуска:

- Frontend: http://localhost:3000
- API health (проверка из терминала): http://localhost:4000/api/health

В GitHub Codespaces браузер обращается к API через same-origin proxy на порту 3000. Порт 4000 не нужно открывать в браузере или прописывать его публичный URL. `API_INTERNAL_URL` должен указывать на `http://localhost:4000`; `WEB_ORIGIN` можно оставить пустым — API автоматически определит forwarded origin Codespaces. Корневой `.env` загружается командами `pnpm dev` и `pnpm db:seed`; копировать его в `apps/api/.env` не требуется.

Команды:

```bash
pnpm dev
pnpm build
pnpm lint
pnpm typecheck
pnpm format:check
pnpm db:generate
pnpm db:deploy
pnpm db:seed
pnpm db:migrate
pnpm db:studio
```

После первого `pnpm install` необходимо сохранить созданный `pnpm-lock.yaml` в Git. Пока lockfile не добавлен, CI устанавливает зависимости без frozen-lockfile.

## Первый вертикальный квест

В базе есть seed-квест «Тайна пропавшего числа». После запуска frontend, API и PostgreSQL откройте `/quests`, зарегистрируйтесь, подтвердите почту по ссылке и откройте миссию. API сохраняет сессию, попытки и статус прохождения в PostgreSQL.

Seed-библиотека содержит 25 опубликованных миссий в 8 тематиках (не менее трёх на рубрику), по три уровня и девять заданий на миссию. Для каждой опубликованной миссии доступен гостевой пример первого задания; ответы проверяются сервером без сохранения попыток и начисления наград.

## Подтверждение почты и восстановление пароля

Новые аккаунты создаются со статусом `PENDING` и не получают сессию, пока пользователь не подтвердит email. Ссылка подтверждения действует 24 часа; ссылка сброса пароля — 30 минут. Оба токена одноразовые: в PostgreSQL хранится только SHA-256-хеш. Повторная отправка ссылки подтверждения ограничена rate limit; запрос сброса пароля дополнительно защищён cooldown в 60 секунд.

Для локальной разработки используется `EMAIL_PROVIDER=console`: API выводит ссылку в терминал в строке `QUESTORIA_EMAIL`. Это только dev-режим — не публикуй такие логи и не используй его в production.

Для отправки настоящих писем через Resend настрой переменные окружения:

```dotenv
EMAIL_PROVIDER=resend
RESEND_API_KEY=re_...
EMAIL_FROM="Questoria <no-reply@your-domain.example>"
NEXT_PUBLIC_SITE_URL=https://your-domain.example
```

Домен отправителя должен быть подтверждён в Resend. В Codespaces оставь `NEXT_PUBLIC_SITE_URL` пустым: API автоматически использует origin frontend-порта Codespaces. В production `EMAIL_PROVIDER=console` запрещён, а `RESEND_API_KEY` и `EMAIL_FROM` обязательны.

Смена пароля отзывает все активные сессии пользователя. Запрос восстановления для неизвестного адреса возвращает тот же ответ, что и для существующего аккаунта, чтобы не раскрывать регистрацию email.

## Прототип

Откройте `prototype/index.html` напрямую в современном браузере. Инструкция и ограничения находятся в `prototype/README.md`.

Прототип хранит ответы и прогресс в браузере. Не используйте его для реальных аккаунтов или конфиденциальных данных. В production ответы, состояние прохождения и начисления должны проверяться и сохраняться на сервере.

## Правила разработки

1. PRD и MVP Execution Specification — источники требований.
2. Изменение архитектуры фиксируется в ADR.
3. Разрабатываем вертикальными срезами: интерфейс → API → база → тесты → документация.
4. Ответы, XP, монеты и права доступа никогда не доверяются клиенту.
5. Для каждой функции добавляются acceptance criteria, тесты и обработка ошибок.
6. Изменения вносятся через feature-ветку и Pull Request.

Текущий этап: **Sprint 3 — CMS для контента**. Реализованы роли Author/Reviewer/Admin/Super Admin, TOTP MFA для администраторов, same-origin проверки для изменяющих запросов, CRUD рубрик и квестов, визуальный редактор заданий, редакционная очередь с фильтрами по статусу/автору и приоритетом ожидания рецензии, цикл review/approve/publish с возвратом автору на доработку и обязательным комментарием рецензента, новая версия из опубликованной и append-only audit log. Реализованы регистрация и вход, публичный каталог, демо-квест с пятью типами заданий (`single_choice`, `multiple_choice`, `numeric_input`, `text_input`, `ordering`), защищённое прохождение, XP/монеты с транзакционным начислением, append-only Ledger, профиль, прогресс и история начислений. Первое прохождение демо-квеста (один уровень с пятью заданиями) приносит 40 XP и 15 монет; повторное прохождение этой же версии не создаёт новые валютные записи.

## Проверки качества

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

CI дополнительно применяет миграции PostgreSQL, загружает seed-квест, запускает API и выполняет `scripts/smoke.mjs`. Smoke test проходит все пять типов заданий через HTTP API, проверяет отсутствие решений в публичном payload, серверную валидацию, идемпотентный replay попытки, восстановление прохождения после входа, начисление XP/монет, запрет повторного фарминга наград и изоляцию чужих профилей.

Профиль доступен по адресу `/profile`. API кошелька: `GET /api/v1/me/wallet`; баланс вычисляется из append-only `wallet_ledger`. Награды за первое прохождение демонстрационной версии: 40 XP и 15 монет (уровень + квест + итоговое задание).

**Ограничение:** это development MVP, не публичный production-релиз. Пока нет upload/storage медиа, справочника навыков, полноценного rich-text редактора и preview tokens, трат/косметического магазина, полноценной аналитики/skill progression и законченных юридических/privacy-процессов для беты. До публичного запуска необходимо закрыть эти требования и провести security/privacy review.

При первом включении MFA создаются 10 резервных кодов. Они показываются один раз; в БД хранится SHA-256-хеш каждого кода. Используй код вместо TOTP при потере доступа к приложению. Чтобы заменить набор, введи актуальный код из приложения-аутентификатора — старые коды будут отозваны.

Для bootstrap первого администратора: зарегистрируй обычный аккаунт, подтверди email, выполни `pnpm db:seed`, затем явно назначь роль командой `QUESTORIA_ALLOW_ROLE_GRANT=1 pnpm --filter @questoria/api admin:grant-role <email> SUPER_ADMIN`. Для TOTP добавь 32-байтовый hex-ключ `MFA_ENCRYPTION_KEY` в секреты API; секрет MFA показывается один раз при настройке. Не выдавай Super Admin через публичный API.

CMS доступна по `/admin`. Назначение ролей выполняется только явной bootstrap-командой. Все операции контентного workflow записываются в `admin_audit_logs`; опубликованные версии и их уровни/задания защищены триггерами PostgreSQL от UPDATE/DELETE.

Архитектурные решения: [ADR-009](docs/ADR/009-monorepo-in-existing-repository.md), [ADR-010](docs/ADR/010-runtime-and-toolchain.md), [ADR-011](docs/ADR/011-wallet-ledger-and-rewards.md) и [ADR-012](docs/ADR/012-puzzle-engine-validation-contracts.md) и [ADR-013](docs/ADR/013-cms-rbac-mfa-versioning.md).


## Игровой прогресс и каталог

- Каталог поддерживает поиск по названию, описанию, рубрике и навыкам, фильтры по рубрикам/сложности и сортировку по длительности или названию.
- Публичная карточка миссии предлагает гостевой пример: один ответ проверяется сервером без аккаунта, а попытка, учебный прогресс и награды не сохраняются.
- Вошедшие пользователи могут продолжить до двух последних незавершённых миссий прямо из каталога; для гостей этот блок не отображается.
- Карточки и страницы квестов показывают редакционные обложки, цели обучения, навыки, число этапов и заданий.
- Во время прохождения отображается серверный прогресс по решённым заданиям; подсказки открываются по одной.
- Уровень игрока рассчитывается по XP из wallet ledger. Достижения открываются по серверным показателям прохождений и этапов, а не по данным браузера.
- CMS показывает предпросмотр обложки, alt-текста и источника лицензии. Файловая загрузка пока не подключена: для неё требуется настроить объектное хранилище и правила доступа.

Для production-отправки писем требуется настроить Resend и подтвердить домен отправителя. До публичной беты также нужны MFA recovery и security/privacy review.

## Управление пользователями в CMS

- Список до 100 последних аккаунтов с поиском по email, имени и назначенным ролям.
- Super Admin с подтверждённой MFA может назначать и снимать роли AUTHOR, REVIEWER, ADMIN и SUPER_ADMIN.
- Можно приостанавливать и повторно активировать аккаунты. При приостановке все активные сессии пользователя отзываются; для повторного входа потребуется авторизация.
- Каждое изменение требует причину и добавляет запись в неизменяемый журнал аудита.
- Защита от самоблокировки: нельзя менять собственные роли/статус и нельзя удалить либо приостановить последнего активного Super Admin.
- Обычные Admin, Reviewer и Author не имеют доступа к API управления пользователями и ролями.

Управление пользователями использует существующие таблицы пользователей, ролей, сессий и аудита; новая миграция базы данных не требуется.

### Управление активными сессиями

В карточке пользователя Super Admin может просмотреть активные сессии, время создания и срок действия, а также факт подтверждения MFA в каждой сессии. Отзыв сессии требует причины и записывается в аудит. Текущую сессию администратора нельзя завершить этой операцией; действие «Завершить остальные» сохраняет текущую сессию активной.


## Журнал аудита

В CMS журнал действий поддерживает поиск по событию, email пользователя, ID объекта и причине, а также фильтры по типу события, типу объекта и диапазону дат (UTC). Записи выдаются страницами по 30 элементов; CSV-экспорт применяет те же фильтры и ограничен 5 000 событиями за один запрос. В деталях доступны причина и снимки состояния до/после изменения.


## API health и корреляция запросов

- `GET /api/health` — liveness: процесс API отвечает.
- `GET /api/health/ready` — readiness: API выполняет короткий запрос `SELECT 1` к PostgreSQL. При недоступной базе возвращается HTTP 503 без раскрытия деталей подключения.
- Каждый HTTP-ответ содержит `X-Request-ID`. Безопасный входящий идентификатор сохраняется; отсутствующее или некорректное значение заменяется серверным UUID.
- API пишет однострочные JSON access logs с request ID, HTTP-методом, шаблоном маршрута, статусом и длительностью. Query string, тело запроса, cookies, заголовок Authorization и IP-адреса в access log не включаются.

Для uptime monitoring используй `/api/health/ready`; `/api/health` подходит только для проверки живости процесса.


## Резервное копирование и восстановление PostgreSQL

Для локальной PostgreSQL в Docker Compose:

```bash
docker compose -f infra/docker/docker-compose.yml up -d postgres
pnpm run db:backup -- backups/questoria-before-change.dump
ALLOW_DATABASE_RESTORE=1 pnpm run db:restore -- backups/questoria-before-change.dump --confirm-database questoria
```

Backup сохраняется в custom-формате PostgreSQL и сопровождается SHA-256-файлом; архив проверяется до завершения операции. Restore требует отдельного подтверждения точного имени базы, заменяет объекты из архива и запрещён при `NODE_ENV=production`. Не запускай восстановление при работающем приложении или без понимания потери изменений после даты backup.

Подробности и CI-сценарий восстановления в отдельную базу: [runbook PostgreSQL](docs/operations/postgres-backup-restore.md). Это локальный инструмент, а не production backup service: перед публичной бетой нужно включить управляемые резервные копии, шифрование, off-site retention и PITR у провайдера базы.
