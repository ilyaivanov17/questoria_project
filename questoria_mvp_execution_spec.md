# QUESTORIA — спецификация реализации MVP

**Документ:** MVP Execution Specification / Technical Addendum к PRD v1.0  
**Дата:** 16 ноября 2026 года  
**Статус:** базовый план реализации; перед production требуется техническое и юридическое ревью  
**Рабочее название:** Questoria (не утверждённый бренд)

---

## 0. Для чего нужен этот документ

Основной PRD описывает продукт целиком. Этот документ сужает его до первого работающего релиза и устраняет неоднозначность в первых задачах разработки. Он должен использоваться вместе с `quest_platform_prd.md`.

**Правило разработки:** вначале создаём один полностью работающий квест от публичной SEO-страницы до прохождения, сохранения результата, начисления награды и отображения в профиле. Не строим сразу огромную платформу.

### 0.1. Базовые допущения

| Решение | Принято для MVP | Почему |
|---|---|---|
| Рабочее имя | Questoria | Временное; бренд и домен проверить отдельно |
| Первый рынок | Германия / ЕС | Учитываем требования приватности и локальную инфраструктуру |
| Язык интерфейса | Русский на первом прототипе; архитектура готова к DE/EN | Можно проверить механику без полного перевода каталога |
| Первая аудитория беты | Взрослые и подростки 14+ | Детский режим запускается после отдельного privacy/legal review |
| Клиент | Адаптивный веб-сайт | Не тратим ресурсы на нативные приложения до проверки спроса |
| Архитектура | Модульный монолит | Меньше инфраструктуры, единые транзакции и проще сопровождение |
| Контент | 3 рубрики, 6 стартовых миссий | Достаточно для проверки качества и возврата пользователей |
| Монетизация | Не включать в MVP | Сначала подтверждаем полезность и завершение миссий |
| Социальные функции | Не включать | Снижаем риски модерации и безопасности |

### 0.2. Цель MVP

Пользователь должен суметь:

1. Открыть публичную страницу квеста из поисковой системы или по ссылке.
2. Понять тему, пользу, возрастной диапазон, сложность и примерное время прохождения.
3. Зарегистрироваться или войти.
4. Начать квест и пройти уровни с разными типами заданий.
5. Получать понятную обратную связь, подсказки и объяснения.
6. Потерять соединение/закрыть страницу и продолжить с сохранённого шага.
7. Завершить квест, получить XP и монеты ровно один раз.
8. Посмотреть результат, историю наград и прогресс по навыкам.
9. Администратор должен добавить новую миссию через CMS, проверить её в предпросмотре и опубликовать без изменения кода, используя уже поддерживаемые типы заданий.

**MVP не считается готовым**, если можно пройти только демонстрацию без надёжного сохранения, если награду можно получить повторно или если новый квест нельзя опубликовать через CMS.

## 1. Продуктовый срез MVP

### 1.1. Стартовые направления

| Рубрика | Что изучает пользователь | Квесты первой волны |
|---|---|---|
| Логика и мышление | Закономерности, дедукция, последовательности, внимательность | «Тайна пропавшего числа», «Дело о трёх свидетельствах» |
| Наука вокруг нас | Наблюдение, гипотезы, причинно-следственные связи, базовая физика | «Экспедиция на Марс», «Лаборатория света» |
| Цифровая грамотность | Безопасность паролей, фишинг, логика алгоритмов | «Цифровой детектив», «Алгоритм для робота» |

Не создавать сотни пустых категорий. Публичная рубрика открывается для индексации, когда у неё есть уникальное вводное содержание и как минимум три качественные связанные миссии или иной достаточный полезный материал.

### 1.2. Контентные стандарты на старте

Каждый квест должен включать:

- конкретную учебную цель, написанную понятным языком;
- 2–4 измеримых результата обучения;
- возрастной диапазон, сложность и оценку длительности;
- сюжетное введение без длинной прелюдии;
- от 3 до 5 уровней;
- не менее 2 поддерживаемых типов головоломок по возможности;
- минимум одну подсказку и объяснение правильного решения для каждой задачи;
- проверенные ответы, допустимые варианты и единицы измерения, если применимо;
- итоговый вопрос или практическое применение;
- сведения об авторе, редакторе, источниках и лицензиях медиа;
- title, meta description, H1, canonical, slug и обложку с alt.

**Контент нельзя публиковать**, если отсутствует правильный ответ, объяснение, возрастная проверка или редакторское одобрение.

## 2. Роли, права и доступы MVP

### 2.1. Минимальная RBAC-матрица

| Действие | Learner | Author | Reviewer | Admin | Super-admin |
|---|---:|---:|---:|---:|---:|
| Читать опубликованный каталог | Да | Да | Да | Да | Да |
| Проходить квесты | Да | Да | Да | Да | Да |
| Смотреть собственный прогресс | Да | Да | Да | Да | Да |
| Создавать черновики контента | Нет | Да | Да | Да | Да |
| Отправлять контент на проверку | Нет | Да | Да | Да | Да |
| Одобрять контент | Нет | Нет | Да | Да | Да |
| Публиковать контент | Нет | Нет | Нет | Да | Да |
| Управлять пользователями | Нет | Нет | Нет | Ограниченно | Да |
| Изменять системные роли и настройки | Нет | Нет | Нет | Нет | Да |
| Смотреть аудит действий | Нет | Нет | По назначению | Да | Да |

Для MVP отдельная роль Moderator не нужна, потому что пользовательского контента и чатов нет. Административные маршруты защищаются серверной проверкой роли, а для Admin/Super-admin обязательна многофакторная аутентификация. Проверка доступа только на frontend запрещена.

### 2.2. Состояния аккаунта

`pending_verification → active → suspended → deleted/anonymized`

- Не подтверждённый адрес не открывает функции, требующие подтверждённой учётной записи.
- Заблокированный пользователь не может начинать новые сессии; действующие токены отзываются.
- Запрос удаления инициирует установленный процесс удаления/анонимизации и проверку связанных юридических обязанностей хранения.

## 3. Сценарии и состояния игрового движка

### 3.1. Жизненный цикл контента

`draft → in_review → approved → scheduled → published → archived`

Правила:

- Author редактирует только черновик или возвращённый на доработку материал.
- Reviewer оставляет замечания и переводит материал в `approved` или обратно в `draft`.
- Admin публикует одобренную версию или задаёт время публикации.
- После публикации контентная версия неизменяема. Исправление создаёт новую версию.
- Активная игровая сессия закрепляется за той версией квеста, на которой началась.
- Архивирование не удаляет исторические попытки и начисления.

### 3.2. Жизненный цикл прохождения

`not_started → in_progress → completed`

Дополнительные состояния: `abandoned` (вычисляемое/необязательное), `expired` (только если введены специальные временные события). Не превращать обычный уход со страницы в провал.

Уровень: `locked → available → in_progress → completed`. Доступ к следующему уровню выдаётся только после выполнения серверного критерия завершения предыдущего уровня.

### 3.3. Алгоритм отправки ответа

1. Клиент отправляет `puzzleId`, `attemptId` (UUID), ответ и контекст прохождения.
2. Сервер проверяет сессию, пользователя, владельца прогресса, опубликованную версию и доступность задания.
3. Сервер проверяет уникальность `attemptId` и rate limit.
4. Ответ нормализуется по правилам типа задания.
5. Валидатор сравнивает ответ с серверным ключом решения.
6. Сервер сохраняет попытку, балл и результат в транзакции.
7. Клиент получает `isCorrect`, объяснение, подсказку следующего уровня (при необходимости) и прогресс.
8. Клиент не присылает `isCorrect`, XP, coins, максимальный балл или статус завершения — такие поля игнорируются/отклоняются.

### 3.4. Правила попыток

- Количество попыток хранится в версии задания, по умолчанию 3.
- Ограничение попыток не должно навсегда блокировать учебный контент. После лимита показывается объяснение или режим разбора.
- Подсказки не блокируют завершение миссии.
- Таймер необязателен и не используется как обязательный критерий для основной награды.
- Повторное открытие страницы восстанавливает последнее сохранённое состояние с сервера.

## 4. Типы головоломок: контракт и поведение

### 4.1. Общий контракт Puzzle

Публичная часть задания возвращается клиенту; правильное решение хранится отдельно и никогда не включается в публичный JSON.

```json
{
  "id": "puzzle_uuid",
  "type": "single_choice",
  "schemaVersion": 1,
  "prompt": "Какое число должно быть следующим?",
  "instruction": "Выбери один вариант.",
  "publicPayload": {},
  "hints": [
    {"order": 1, "text": "Посмотри, как меняется разница между числами."}
  ],
  "feedback": {
    "correct": "Верно! Разница каждый раз увеличивается на единицу.",
    "incorrect": "Попробуй найти закономерность между соседними числами."
  },
  "maxAttempts": 3,
  "maxScore": 10,
  "accessibility": {
    "plainTextAlternative": "Последовательность чисел: 2, 3, 5, 8, ...",
    "keyboardInstructions": "Выбери вариант стрелками и подтверди Enter."
  }
}
```

Серверное решение находится в отдельном поле/таблице `puzzle_solutions`, доступной только backend-валидатору и авторизованным редакторам в CMS. Ответы не должны попадать в HTML, hydration payload, публичный API, логи аналитики или source maps.

### 4.2. Поддерживаемые типы

| Тип | Публичный payload | Серверное решение | Проверка | Доступность |
|---|---|---|---|---|
| `single_choice` | Массив `{id,label}` | Один `optionId` | ID совпадает | Радиокнопки + клавиатура |
| `multiple_choice` | Массив `{id,label}` и `min/max` | Массив ID | Сравнение множеств или заданная частичная оценка | Чекбоксы, понятный счётчик |
| `numeric_input` | Единица, min/max длина, placeholder | Значение/допуск/единицы | Парсинг числа, нормализация decimal, допустимая погрешность | Подписанный input, не только drag |
| `text_input` | Placeholder, лимит длины, допустимый формат | Список допустимых нормализованных ответов | Безопасная нормализация; без LLM-арбитра | Подпись, autocomplete off при необходимости |
| `ordering` | Список карточек с ID и label | Правильный упорядоченный список ID | Сравнение последовательности | Кнопки вверх/вниз как альтернатива drag |

Все payload проходят JSON Schema validation с `additionalProperties: false`, лимитами строк/массивов и allowlist типов. Не принимать произвольный HTML, JavaScript, iframe, eval или URL для автоматической загрузки ресурсов.

## 5. Награды и экономика MVP

### 5.1. Разделяем XP и монеты

- **XP** — накопительный опыт аккаунта, не тратится.
- **Монеты** — внутренняя невыводимая валюта, в MVP тратится только на косметические элементы или коллекции, которые не дают преимущества в обучении.
- В MVP не продавать монеты за деньги и не предлагать случайные награды.

### 5.2. Начисление за миссию

Начальные тестовые значения (гипотеза, подлежат балансировке на бете):

| Событие | XP | Монеты |
|---|---:|---:|
| Завершение уровня | 5 | 2 |
| Завершение квеста | 25 | 10 |
| Успешное итоговое задание | 10 | 3 |
| Первое прохождение недели/спецмиссии | +5 | +2 |

Правило: основная награда за конкретную опубликованную версию миссии начисляется один раз одному профилю. Повторное обучение может давать практику и прогресс по навыку, но не бесконечную валюту. Идемпотентный ключ, например `quest_complete:{profileId}:{questVersionId}`.

### 5.3. Ledger — обязательный источник истины

Каждая операция — новая неизменяемая запись:

- `id`, `profile_id`, `currency` (`XP` / `COIN`), `amount` (+/-), `reason`, `source_type`, `source_id`, `idempotency_key`, `created_at`.
- Уникальный индекс по `idempotency_key`.
- Баланс выводится из ledger либо поддерживается отдельным агрегированным полем, которое сверяется с суммой ledger.
- Нельзя обновлять или удалять старые операции для исправления баланса; создаётся компенсирующая запись с причиной и audit log.
- Начисление награды и отметка завершения квеста выполняются в одной DB-транзакции.

### 5.4. Антиабьюз

- Лимитировать частоту отправки ответов и повторные попытки.
- Не доверять времени на клиенте.
- Не выдавать награду из frontend callback.
- Проверять порядок состояния уровней и владельца сессии.
- Фиксировать аномально быстрые прохождения для ручной проверки; не банить автоматически только по одному сигналу.
- Административная корректировка баланса — отдельное permission, обязательное указание причины, audit log.

### 6.1. Удаление и версии

- Удаление пользователя не должно каскадно уничтожать финансово-подобный ledger и обезличенную статистику до выполнения утверждённой политики хранения.
- Исторические попытки должны ссылаться на конкретную версию квеста и задания.
- Публикация новой версии не меняет уже начатую сессию.
- Опубликованные версии, награды и audit logs не редактируются задним числом обычным CRUD.

## 7. API-контракты первого вертикального среза

Базовый префикс: `/api/v1`. Все ID — UUID. Все даты — ISO 8601 UTC. Ошибки имеют форму `{ "error": { "code": "...", "message": "...", "requestId": "..." } }` без утечки внутренних деталей.

### 7.1. Публичные маршруты

| Метод | Endpoint | Назначение | Доступ |
|---|---|---|---|
| GET | `/public/categories` | Активные категории | Публичный |
| GET | `/public/categories/{slug}` | Категория + опубликованные карточки | Публичный |
| GET | `/public/quests/{slug}` | SEO-данные и карточка квеста без ответов | Публичный |
| GET | `/public/quests/{slug}/preview` | Безопасный пример задания | Публичный, без solution |

### 7.2. Аккаунт и профиль

| Метод | Endpoint | Назначение | Доступ |
|---|---|---|---|
| POST | `/auth/register` | Создать аккаунт | Public + rate limit |
| POST | `/auth/login` | Войти | Public + rate limit |
| POST | `/auth/logout` | Завершить сессию | Authenticated |
| GET | `/me` | Текущий пользователь и роли | Authenticated |
| GET | `/me/profile` | Профиль пользователя | Authenticated |
| PATCH | `/me/profile` | Изменить разрешённые поля профиля | Owner |
| GET | `/me/progress` | Общий прогресс | Owner |
| GET | `/me/wallet` | Баланс и история ledger | Owner |

### 7.3. Игровые маршруты

| Метод | Endpoint | Назначение | Доступ |
|---|---|---|---|
| POST | `/runs` | Начать/возобновить квест по slug или version ID | Authenticated |
| GET | `/runs/{runId}` | Состояние прохождения и публичные задания | Owner |
| POST | `/runs/{runId}/puzzles/{puzzleId}/attempts` | Отправить ответ | Owner + rate limit |
| POST | `/runs/{runId}/hints/{hintId}/use` | Зафиксировать использование подсказки | Owner |
| POST | `/runs/{runId}/complete` | Запросить завершение; сервер сам проверяет критерии | Owner |
| GET | `/runs/{runId}/result` | Итог, награды, учебное резюме | Owner |

### 7.4. Админские маршруты

| Метод | Endpoint | Назначение | Доступ |
|---|---|---|---|
| GET/POST | `/admin/categories` | Список/создание рубрик | content.manage |
| PATCH/DELETE | `/admin/categories/{id}` | Изменение/архивирование рубрики | content.manage |
| GET/POST | `/admin/quests` | Список/создание квестов | content.manage |
| GET/PATCH | `/admin/quests/{id}` | Получить/изменить черновик | content.manage |
| POST | `/admin/quests/{id}/submit-review` | Отправить на проверку | content.submit |
| POST | `/admin/quests/{id}/approve` | Одобрить | content.review |
| POST | `/admin/quests/{id}/publish` | Опубликовать одобренную версию | content.publish |
| POST | `/admin/quests/{id}/preview-token` | Создать ограниченный предпросмотр | content.preview |
| GET | `/admin/audit-logs` | История админских действий | audit.read |

### 7.5. Пример отправки ответа

**Request**

```json
{
  "attemptId": "b3e1e92b-1fc2-4e3e-a1c1-43a88c53d17c",
  "answer": {"optionId": "opt_03"}
}
```

**Response — правильный ответ**

```json
{
  "attemptId": "b3e1e92b-1fc2-4e3e-a1c1-43a88c53d17c",
  "result": "correct",
  "scoreAwarded": 10,
  "attemptsRemaining": 2,
  "feedback": "Верно. Ты заметил, что разница между числами увеличивается на единицу.",
  "puzzleProgress": {"completed": true, "levelScore": 10}
}
```

**Response — повтор запроса с тем же attemptId**

Сервер возвращает тот же сохранённый результат, не создавая новую попытку и не начисляя награду повторно.

### 7.6. Общие требования к API

- OpenAPI генерируется из backend DTO/схем и хранится в репозитории.
- DTO строго валидируются; неизвестные поля не должны приниматься молча.
- Для изменяющих состояние запросов предусмотрены CSRF-защита (если cookie auth), rate limits и audit where applicable.
- Ownership check обязателен для каждого `runId`, `profileId`, `wallet` и `attemptId`.
- Время, награды и правильность ответов определяет сервер.
- На публичные endpoints не выдаются приватные данные и ключи решений.

| Learning objectives | array | Да | 2–4 цели |

| Canonical | URL | Авто/override | По умолчанию self-canonical |
| Author / Reviewer | user relation | Да | Reviewer обязателен для публикации |

### 8.3. Форма уровня

- `title`, `intro`, `learning_note`, `order_no`, `completion_rule`, `estimated_minutes`.
- Порядок уровней задаётся drag-and-drop, но должен иметь кнопочные и клавиатурные альтернативы.
- Нельзя удалить уровень, на который ссылаются опубликованные версии или попытки; вместо этого версия квеста создаётся заново.

### 8.4. Форма головоломки

Общие поля: тип, schemaVersion, текст вопроса, инструкция, публичный payload, серверный ключ ответа, допустимые попытки, максимальный балл, подсказки, обратная связь, навигационный порядок, alt/text alternative.

Редактор выбирает тип из allowlist. UI формы меняется в зависимости от типа. Сервер валидирует контент тем же JSON Schema, что и игровой движок. Редактор не может вставить скрипт.

### 8.5. Проверка готовности публикации

Кнопка «Опубликовать» недоступна, пока не выполнены все проверки:

- есть title, slug, summary, описание и рубрика;
- задана учебная цель и минимум один навык;
- есть минимум один уровень и допустимое число головоломок;
- каждый puzzle type поддерживается текущей версией engine;
- для каждого задания задано решение, объяснение и хотя бы одна подсказка или обоснование, почему подсказка не нужна;
- JSON Schema валиден;
- возраст, язык, длительность и сложность указаны;
- SEO title/H1/meta/canonical заполнены;
- обложка имеет alt и лицензионную запись;
- reviewer одобрил текущую версию.

### 8.6. Предпросмотр и версии

Предпросмотр должен отображать публичную страницу, игровой экран и итоговый экран с данными черновика. Preview token ограничен по времени, не даёт доступа к кошельку реального пользователя и не индексируется. Публикация создаёт immutable version и обновляет `current_published_version_id`. Rollback — переключение pointer на ранее опубликованную версию, а не редактирование старой записи.

## 10. Структура репозитория и технологическая база

Рекомендуемый monorepo:

```text
questoria/
  apps/
    web/                 # Next.js: публичный сайт, игра, профиль, admin UI
    api/                 # NestJS modular monolith, REST + OpenAPI
  packages/
    contracts/           # shared DTO / zod or JSON schemas
    puzzle-engine/       # frontend renderers + server validators by type
    ui/                  # shared design-system components
    config/              # eslint, tsconfig, formatting
  prisma/
    schema.prisma
    migrations/
    seed.ts
  docs/
    PRD.md
    MVP_EXECUTION_SPEC.md
    ADR/
    API.md
    CONTENT_GUIDE.md
  tests/
    e2e/
  infra/
    docker/
    deployment/
```

### 10.1. Технические правила

- TypeScript strict mode.
- Один package manager и lockfile на весь репозиторий.
- Линтер, formatter, typecheck и tests запускаются в CI.
- PostgreSQL — источник истины для пользователей, прогресса и ledger.
- Prisma migrations (или другой ORM, но выбрать один до Sprint 0).
- Redis не добавлять до появления реальной потребности в очередях/кеше.
- Секреты только в secret manager/переменных окружения; не коммитить `.env`.
- Публичные страницы рендерятся сервером/статически; игровой маршрут — закрыт и `noindex`.
- Решения и награды проверяются только в backend.
- Не использовать неподдерживаемую библиотеку только потому, что AI предложил её.

### 10.2. Базовые окружения

- `local`: Docker Compose + локальный PostgreSQL + seed data.
- `staging`: отдельные секреты и база, тестовые пользователи и синтетический контент.
- `production`: EU-hosted deployment, резервное копирование, мониторинг, ограниченный доступ.

## 12. Definition of Done для любой задачи

Задача считается завершённой, когда:

1. Выполнены все acceptance criteria.
2. Код типизирован и отформатирован, линтер и typecheck проходят.
3. Добавлены unit/integration/e2e тесты по уровню риска.
4. Проверены состояния loading, empty, error, success.
5. UI работает на мобильном экране и с клавиатуры.
6. Сервер проверяет права и владельца ресурса.
7. Нет секретов или правильных ответов в client bundle.
8. Логи не содержат лишних персональных данных.
9. API/схема/документация обновлены.
10. Миграции имеют безопасный план применения и rollback/forward-fix.
11. Для CMS изменений есть audit event.
12. В staging проверен happy path и минимум один негативный сценарий.

## 15. Релизные ворота MVP

MVP допускается в закрытую бету, только если:

- [ ] Пользователь проходит полный квест на телефоне и десктопе.
- [ ] Сессия и прогресс восстанавливаются после перезагрузки.
- [ ] Ответы и награды не доверяют данным клиента.
- [ ] Ledger не допускает дублирования начислений.
- [ ] Контент можно создавать и публиковать через CMS.
- [ ] Опубликованные версии нельзя незаметно изменить задним числом.
- [ ] Приватные страницы не раскрывают данные и не индексируются.
- [ ] Админские права ограничены, MFA включена.
- [ ] Важные действия администраторов аудируются.
- [ ] Проверены backup/restore и rollback.
- [ ] Проведены accessibility, security и privacy проверки.
- [ ] Все стартовые миссии проверены по фактам, возрастной уместности и лицензиям.

**Рекомендация:** не открывать детские аккаунты и рекламные/социальные функции в первой бете. Сначала подтвердить ценность квестов на ограниченной аудитории взрослых и подростков 14+, а отдельный детский режим выпускать после разработки и юридической проверки соответствующих процессов.
